# 数据与时间语义

[English](../en/data-model.md) · [文档索引](README.md)

## 行情与研究对象

- 现有日线示例和 `contracts/quote.schema.json` 使用 `quote:<YYYY-MM-DD>:<代码>`，payload 包含 `code`、`date`、OHLC、`volume` 等字段。采集端示例通过普通 `PUT` 写入同一字面量键；它**不等于**每次都自动追加时态版本。
- 时态路径通过 `PUT_VERSIONED` 为一个逻辑键追加不可变版本，底层按递增 `seq` 写 `:v...` 版本键和 `:current` 指针；`GET_AS_OF`、`LIST_VERSIONS`、`LIST_WRITES`、重放指纹分别负责历史读、审计与状态核验。原始行情的普通 `PUT` 与研究对象的版本化写入是不同语义，不要混为一谈。
- Agent `Proposal` 有因子、假设、实验、推荐、复盘等类型，`SubmitProposal` 是 Go API 的受约束入口。`BuildContext` 汇总已有实验、策略状态及磁盘上的契约/风控文件。完整的“研究进程”、Handoff 交易结果及推荐对象统一 schema **尚未定义**；不能把讨论中的状态阶段当作已实施契约。

## 两种时间不能混淆

行情交易时间（`date`，以及 payload 可能包含的成交时间）描述市场事件；版本记录的 `write_ts` 描述系统**何时知道它**。当前 `GET_AS_OF(key, t)` 按写入时间筛版本，适合防止研究回看时看到晚到的修正，但它不是“按股票+交易时间取 N 天”的现成 API。`BuildContext` 的账本读取遵循 as-of；从磁盘读取的 `contracts/` 和 `riskredlines/` 文件没有同样的历史版本保证。

## 单股 N 天：目标，不是当前能力声明

日期优先的字典序适合某日全市场，却不把同一代码的多日行情连续存放。目标查询应定义：股票代码、交易时间闭开区间、排序、分页/上限、缺失日和修正数据的处理，再对真实样本测量扫描量、延迟与内存。当前服务端业务 `SCAN` 最多返回 10,000 条并会截断，且隐藏时态内部版本键；不能直接依赖它完成无限制历史导出。

讨论中的股票优先布局（如 `quote:<代码>:<日期>`）**尚未实施**。若采纳，应先决定日线/分钟线的时间精度与分布式分片边界，再在停写、备份、转换、核验后切换旧数据。不要在此阶段宣称已有二级索引或数据迁移工具。
